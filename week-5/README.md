# Week 5: Adding the Predictive Categorical Levels

## This week's goals

> After submitting a model that uses only numerical features, explore adding categorical features. Use statistical tests to determine which levels of each categorical variable are most predictive. Keep only these levels and discard the rest.

> Again, consider logistic regression, decision tree, random forest, and gradient boosted tree models, and use cross-validation for hyperparameter tuning. Submit the predictions generated by the optimal model found.

## What to read, in order

1. **[`bm-fraud-categorical-tests.ipynb`](bm-fraud-categorical-tests.ipynb)** runs the statistical tests once on the first 80% of the training data, to show which levels get kept and why. It also checks whether the kept levels still show up in the test transactions.
2. **[`bm-fraud-categorical-tuning.ipynb`](bm-fraud-categorical-tuning.ipynb)** repeats the tests inside each cross-validation fold, then tunes the same four model types as Week 4 on the numerical features plus the kept levels. It ends with a comparison of the best setting for each model type.
3. **[`bm-fraud-categorical-submission.ipynb`](bm-fraud-categorical-submission.ipynb)** runs the tests on all of the training data, trains the best model and writes the Kaggle submission. The last cell has the Kaggle score.
4. **[`tuning-results/`](tuning-results/)** has every setting each model tried, with its scores.

All three notebooks are saved with their outputs, so they don't need to be rerun to see the results.

## Decisions

- **Which levels get kept.** A level is only tested if it has at least 500 training transactions, since the fraud rate of a rarer level is too noisy to trust. It's kept if it passes three checks:
  - it's still significant after a Benjamini–Hochberg correction at 5% across every level tested;
  - its fraud rate is at least 1.5× the overall rate or at most 0.67× of it;
  - it ranks in its column's top 25 by chi-square statistic.

  Missing values count as their own level, since a blank field can be a signal. Every level that isn't kept goes into one "other" column per categorical column, so no rows are lost.
- **Selection is fit inside each fold.** Each fold runs the tests on its own training rows only. If the tests used all of the training data, the validation rows would help pick the levels, and the scores would look better than they really are.
- **The same search as Week 4.** Same four time-ordered folds, same metrics and the same number of settings per model, so any change in score comes from the categorical levels.

## How the levels were selected

Each of the 49 categorical columns (the ones held back in Week 4) gets a chi-square test for every level with enough transactions. The test compares that level's fraud rate with the rate in all the other rows.

On the first 80% of the training data:
- 665 levels were tested;
- 540 were still significant after the correction;
- 436 of those also had a large enough difference in fraud rate;
- 301 were kept, from 47 columns, after the top-25 cap trimmed `card1`, `card2`, `addr1` and `id_20`.

The riskiest kept levels are specific `card1` and `card2` codes and `id_19`/`id_20` values, with fraud rates of 20–38% against an overall rate of 3.5%. The safest are email domains like verizon.net, msn.com and att.net, with fraud rates under 0.7%.

Most kept levels cover about the same share of the test transactions as the training ones. The biggest drop is the browser column `id_31` (95% to 77%), probably because newer browser versions show up in test.

When the submission notebook ran the tests on all of the training data, it kept 318 levels from 48 columns, for 638 features in total.

## A problem I ran into

The first tuning run crashed on Kaggle with an out-of-memory error. It was holding the training and validation matrices for all four folds at once, along with the extra copies logistic regression makes. I changed it to store only each fold's kept levels and build that fold's matrices right before fitting, then free them right after. Building them only takes a couple of seconds, so the run still took about two hours.

## Results

| Model | Mean AUC (4 folds) | Last-fold AUC | Week 4 last-fold AUC | Fraud caught reviewing top 1% |
|---|---|---|---|---|
| LightGBM | 0.9071 | 0.9126 | 0.8960 | 24.7% |
| Random forest | 0.8824 | 0.8857 | 0.8664 | 23.6% |
| Logistic regression | 0.8447 | 0.8371 | 0.8216 | 17.6% |
| Decision tree | 0.8391 | 0.8354 | 0.8377 | 19.3% |

LightGBM was the best model again, with the same settings as Week 4. It trained on all of the training data with 418 trees and scored **0.9086 private / 0.9326 public** on Kaggle, up from 0.8936 / 0.9115 in Week 4. The private score is 0.0040 below its last-fold AUC, close to Week 4's gap of 0.0024, so the time-ordered folds are still a good guide.

Every model's mean AUC went up. LightGBM's last-fold AUC went up 0.017, which closes about 60% of the gap to Week 3's 0.9227. About 93% of the transactions it puts in the top 1% are fraud.

The top three LightGBM settings scored within 0.0001 of each other, so more tuning probably won't help much. I think most of the remaining gap is `card1`. It has 13,553 values, and the 25 levels kept here cover only about 10% of transactions, while Week 3's LightGBM could split on all of them. That's what next week's customer-level and frequency features are meant to cover.
